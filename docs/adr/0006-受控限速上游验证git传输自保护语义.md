# 0006 — 受控限速上游验证 git 传输自保护语义

- 状态：提议中
- 关联：`../test-cases.md`（TC-FEAT-LOWPEED），`../../.github/workflows/e2e-feature-git-lowspeed.yml`，[ADR-0005](0005-gitcdn限速保护验证采用真实用户序列时间上界采样.md)
- 背景：[opensourceways/backlog#2885](https://github.com/opensourceways/backlog/issues/2885)、ascend-ci-deployment `422793a8c`

## 背景与决策

git-cdn 回源限速保护（ADR-0005）依赖回源 git 子进程的 `http.lowSpeedLimit/lowSpeedTime`：
低于阈值持续 lowSpeedTime 秒即中止、交给 backoff 重试。该机制在生产上的触发条件是上游
gh-proxy/github 的随机限速，低概率且不可复现（0005 只能以时间上界采样统计）；而"配置是否
真的让 git 在慢速流上自杀、且不误杀正常流量"是可以确定性验证的——前提是不向生产基础设施
注入故障（延续 ADR-0004/0005 的边界）。

据此决策新增机制 TC-FEAT-LOWPEED：

1. **实验室 fixture，不触生产**：在被测 job 容器内自建 dumb 协议静态 git HTTP 服务，仅绑定
   `127.0.0.1`、OS 分配临时端口；用 chunk+sleep 节流模拟"百 KB/s 且不断连"的病态上游形态。
   被测对象是 job 容器内的真实 git 与真实 http 传输路径，不改任何生产配置。
2. **三段论判定**：
   - 阳性：限速流（速率 < 阈值）带 `http.lowSpeed*` 配置在 `[lowSpeedTime-5, +60]` 秒内非 0
     退出，且日志含低速中止签名（`operation too slow` / `low-speed` / `curl: (28)`）；
   - 阴性对照：同一限速源、**无配置**时在窗口内不被自行中止（外层 timeout 强杀）——证明
     中止由配置驱动，而非环境副作用；
   - 误杀检查：常速小仓库带同一配置正常完成——证明"阈值 1MiB/s / 60s 不会误杀正常流量"的
     参数选型（与 git-cdn 生产值一致）成立。
3. **前提硬断言 git ≥ 2.32**：`GIT_CONFIG_GLOBAL` 环境变量是 git 2.32 引入的，低于此版本
   注入配置被静默忽略——这是 git-cdn 注入路径的关键前提，值得在每个集群的 job 容器上普查。

## 证据与范围

- 验证范围是 **fleet job 容器内的 git 机制语义**（与 vllm-ascend CI 同款 CANN 镜像）；
  git-cdn pod 内回源子进程的同等验证超出 runner E2E 可达范围，需 pod 级命令：
  `kubectl -n git-cdn exec deploy/git-cdn-service -c git-cdn -- git config --show-origin
  --global --get-regexp '^http\.lowspeed|^uploadpack'`。
- 与 ADR-0005 的分工：0005 在生产路径上以"时间上界 + 故障签名"采样验证端到端结果
  （随机限速下不再悬挂）；0006 以受控实验确定性验证机制语义与参数选型（限速必然中止、
  常速必然不误杀）。两者结合覆盖 issue #2885 的"随机限速故障率下降"验收。
- dumb 协议静态服务足以代表传输语义（低速中止发生在 HTTP 传输层，与 smart/dumb 无关）；
  服务实现为 chunk+sleep 节流的 `http.server.SimpleHTTPRequestHandler`，仅回环监听，
  job 结束即随容器销毁。
- 人工执行入口保留输入参数（lowspeed_limit/lowspeed_time/throttle/pack_mb）以支持阈值
  选型实验；默认值与 git-cdn 生产值一致（1MiB/s、60s）。
