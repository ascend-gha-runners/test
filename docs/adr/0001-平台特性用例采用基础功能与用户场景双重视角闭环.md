# 0001 — 平台特性用例采用基础功能与用户场景双重视角闭环

- 状态：已接受 (2026-09-26)
- 决策人：CI/基础设施测试组
- 关联：PR [#23](https://github.com/ascend-gha-runners/test/pull/23), [`test_cases.json`](../../.github/config/test_cases.json), [`test-cases.md`](../test-cases.md)

## 背景

在此前演进中，仓库曾尝试设立独立的跨工具链综合用例 `e2e-user-scenarios.yml` 与配套脚本 `test_user_scenarios.py`，意图串联 OS 包管理器、Python+uv、Rust 编译与 Git 代理模拟真实 CI 流水线。

然而，这种设计带来了严重的架构割裂：
1. **单特性用例沦为浅层探针**：单独的 `e2e-feature-pypi-cache`、`e2e-feature-crates-cache` 等测试只验证端口连通与最小工具链执行，无法代表实际生产工程的真实可用性；
2. **综合用例粒度过粗、边界模糊**：独立用例覆盖 5 大服务，任何一个网络或第三方环节波动就会导致整个 Job 挂掉，难以快速定位根因；且“泛化场景”与“单特性测试”产生大量重复逻辑。

## 决策

**拒绝将“基础功能”与“用户场景”人为割裂为两个独立用例。每个平台能力（PyPI、Crates、Rustup、APT、YUM）测试必须自成完整闭环，在同一个工作流内同时覆盖双重视角：**

1. **【基础功能】(Basic Infrastructure & Protocols)**：
   - 端口连通性探测；
   - 缓存响应头状态与命中率验证（MISS → HIT）；
   - 协议级 404 回退机制（如通过 `X-Cache-Tier` 确认回源至 pypi.org / crates-official 等）；
   - 客户端容灾降级（故障镜像源超时报错与多源兜底 fallback）。
2. **【用户视角场景】(End-User Production Scenarios)**：
   - 真实生产项目（如 `vllm-project/vllm-ascend`）的镜像源与环境变量配置；
   - 严格强制 `--no-cache-dir` / `UV_NO_CACHE=1`，断言禁止本地磁盘 wheel 命中（检测到 `Using cached` 立即报错退出），防止假阳性；
   - 经内网专属源真实安装复杂专有依赖（如华为昇腾 `triton-ascend`、PyTorch CPU 等）；
   - 经内网 crates 镜像创建工程并拉取依赖编译可执行程序；
   - 执行 Python / Rust 运行时导入与计算自检（如张量运算 `torch.ones(2, 2)`），验证无运行时符号缺失。

**同时废弃并删除独立的 `e2e-user-scenarios.yml` 工作流与 `scripts/test_user_scenarios.py`。**

## 理由与后果

- **责任内聚、精准排障**：若 PyPI 代理出问题，直接由 `e2e-feature-pypi-cache` 失败报警，绝不发生“PyPI 探针绿了但上层真实工程挂了”或“综合用例挂了却分不清哪个端口损坏”的模糊地带；
- **防虚假通过 (DX 提升)**：强制 `--no-cache-dir` 保证测试的绝对是内网缓存服务链路，而非本地容器磁盘残留；
- **维护成本降低**：消除冗余维护的双份脚本，所有特性步骤结构高度对齐。
