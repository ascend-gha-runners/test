# 0004 — 用户面冷缓存下载与文件完整性抽样

- 状态：提议中
- 关联：`../test-cases.md`，`../../.github/workflows/e2e-feature-go-cache.yml`

## 背景与决策

已有端口探针、metadata 校验与安装命令可能因预装包、旧缓存、被忽略的失败而绿色，不能据此证明用户实际可用。按 ADR-0001 在各生态原工作流内补真实冷缓存下载/构建与运行；Go 增加仅人工选择单集群的独立特性闭环，不新增全生态综合工作流。

PyTorch CPU 安装保持 ADR-0002 的 amd64 边界；在空 venv 中安装固定 CPU 版本及解析到的依赖，现代客户端负责其正常下载与 hash 检查。另加人工可选的架构无关 HTTP 抽样：读取索引公布的 SHA-256，流式下载选定 wheel 并比较真实字节；有 metadata hash 时也比较 metadata。抽样不能宣称全部 wheel 或全部依赖已覆盖。未提供 hash、无法选择样本或未开启时为未验证，不伪装通过。

## 证据与范围

- `pass` 是某项硬能力实际执行成功；`fail` 是已执行硬断言不满足；`not_applicable` 是既有架构决策的适用性排除；`not_verified` 是缺少执行或证据。软断言/探针仍保持原分级。
- 客户端 loopback 故障备用源与 cargo 离线重建仅证明客户端恢复。404 响应与 `X-Cache-Tier` 分别记录；只有终层证据才报告回源观察成功。nginx 上游 5xx/507 继续由部署仓 mock 回归验证，不主动故障注入生产。
- crates 仅在已审查 gy-006 入口调度；其余集群标记未验证，不能因为五生态 staging 配置就断言线上不存在 8085。hk-ci 缺组织 Runner 证据时保留覆盖缺口，不能映射到 hk-001。
- 保留既有定时任务，但新 Go 工作流与大 wheel 字节抽样仅人工执行。不引入 ArgoCD revision、部署等待或发布编排作为本轮验收前提。

选择有界抽样而不是全量 wheel 下载，以避免大文件带宽负担；选择隔离缓存而不是禁止 nginx HIT，因为用户需要验证的是代理正确交付文件，并非强迫上游 MISS。
