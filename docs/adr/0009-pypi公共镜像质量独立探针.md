# ADR-0009：PyPI 公共镜像质量作为独立信息探针

- 状态：提议中
- 日期：2026-11-13

## 背景

SGLang CI 安装依赖时发生 wheel 下载超时。mind-third 集群 Squid 已将 PyPI 资源转发至华为云镜像，但网络波动可能发生在镜像、CDN 节点或集群公网出口。已有 `TC-FEAT-PYPI` 验证的是缓存代理的功能正确性，不适合通过单个成功/失败判断外部镜像选型。

## 决策

1. 新增独立 `TC-FEAT-PYPI-MIRROR`，使用固定大小的 wheel 比较各公共镜像的下载成功率、延迟与并发有效吞吐。
2. 索引由各镜像独立提供，固定文件版本，下载字节按索引公布的 SHA256 验证。镜像未同步、索引超时、未公布哈希均记未验证，不能视为通过。
3. 由 `.github/config/runners.json` 动态生成全集群矩阵（当前 13 集群），每集群优先选择一个 CPU Runner；没有 CPU Runner 时使用既有 NPU Runner（当前 8 CPU、5 NPU 兜底）。**Runner 直连**测试显式禁用 HTTP 代理。该视角与 Squid Pod 内直接回源不同，结果不能直接替代 Squid 回源质量。
4. 每天每集群只运行低流量小文件采样；大文件并发测速仅在人工触发时进行。工作流同时最多启动 2 个集群任务；人工可选择单集群，避免无意间全量并发下载。
5. 外部镜像故障记为观测结果，不将其作为昇腾 CI 缓存功能的硬失败。仅本地探针执行失败才判 Workflow 失败。
6. 测试经现有 E2E 工作流、catalog 和 Pages 流程可被发现。完整下载指标保存在 Workflow Step Summary 和 artifact，未来若需要历史趋势可扩展 Pages 数据契约。

## 不采用

- **直接并入 `TC-FEAT-PYPI`**：将外部服务质量波动错误关联到 CI 内部缓存功能。
- **定时在全 13 集群运行大型文件压力测试**：带宽、费用与生产干扰不可控；全量大型测试保留人工显式触发。
- **将 Runner 测试解释为 Squid Pod 回源质量**：网络命名空间、节点和 SNAT 路径可能不同。

## 结果

可以长期积累公共镜像可用性证据，支持灰度镜像源选型；仍需单独的 Squid Pod 回源验证和实际 CI 安装 E2E，才能完成故障归因和切换验收。
